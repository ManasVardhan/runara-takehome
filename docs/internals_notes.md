# vLLM 0.31.0 speculative decoding internals (source notes)

# How vLLM 0.31.0 V1 runs speculative decoding: draft_model, eagle3 and ngram

Paths are relative to `vllm/`. I read the source copied off the pod (I ran nothing on it) and also checked the HF configs there.

## 1. Proposal
- **Drafting is autoregressive: one prefill-style pass, then K-1 single-token passes.** `v1/spec_decode/llm_base_proposer.py:512` `propose()` runs a first forward over every target token scheduled this step, then loops at `:689` `for token_index in range(self.num_speculative_tokens - 1):`, feeding back `input_ids = draft_token_ids_list[-1]`. For K=1, or with parallel drafting, it returns after the first pass (`:629`). Drafts are argmax by default: `draft_sample_method = "greedy"` (`config/speculative.py:601`) and `_greedy_sample` at `:438`.
- **draft_model vs eagle3 differ only in hidden-state input.** `v1/spec_decode/draft_model.py:30` passes `pass_hidden_states_to_model=False` and `eagle.py:20` passes `True`. As a result, draft_model needs one extra input slot per request (`llm_base_proposer.py:113-120`; table at `config/speculative.py:1882` reads "Draft model … 1", "EAGLE3 … 0"). EAGLE shifts the target ids by one (`:842-852`). eagle3 also concatenates the target's aux hidden states (`gpu_model_runner.py` ~`:5162`, then `combine_hidden_states` at `:551`).
- **Call site.** In `v1/worker/gpu_model_runner.py:4590`, `with record_function_or_nullcontext("gpu_model_runner: draft"):` follows the target's sample/rejection step. EAGLE and draft_model consume GPU sampled tokens before bookkeeping (`:4618-4635`). The CPU ngram drafter runs after bookkeeping (`draft_after_bookkeeping = True`, `:4677`) and calls `NgramProposer.propose` at `:4980`.
- **ngram is a CPU KMP-style suffix match.** `v1/spec_decode/ngram_proposer.py:210` uses Numba. It can return fewer than K tokens (`:294` `k = min(k, total_token - start_position)`) or none (`:287`), and that `[]` becomes the request's draft (`:134`).
- **Draft KV cache.** The draft's attention layers are added to the same `KVCacheConfig` (`load_model` `:1335`, `uses_draft_kv_cache` at `config/speculative.py:1960`). They must sit in one KV group (`:1687`) and use the target's `block_table_tensor`, so they share block IDs with the target, from one memory pool.
- **CUDA graphs for the draft are PIECEWISE only.** `:421-436` says "Only supports PIECEWISE cudagraphs", and the batch is padded through the drafter's own `CudagraphDispatcher` (`:1784`).

## 2. Verification scheduling
- **Draft tokens join the request's token count.** `v1/request.py:299` `num_tokens_with_spec = len(_all_token_ids) + len(spec_token_ids)`. The running loop schedules `num_tokens_with_spec + num_output_placeholders - num_computed_tokens` (`v1/core/sched/scheduler.py:677`), which is 1+K for a decoding request.
- **The scheduled draft tokens are recorded per request.** `:830-845`: `num_scheduled_spec_tokens = num_new_tokens + num_computed_tokens - num_tokens - ...`, `scheduled_spec_decode_tokens[req_id] = spec_token_ids[:n]`, then `request.spec_token_ids = []`.
- **New drafts arrive between steps.** They come via `update_draft_token_ids` (`:2491`), and prefill chunks drop their drafts (`:2501`). Under async scheduling (used with eagle3 and draft_model; CPU `ngram` disables it, `config/vllm.py:1576-1601`), the scheduler pre-books K `-1` placeholders (`v1/core/sched/async_scheduler.py:50`) and fills them later in `update_draft_token_ids_in_output` (`scheduler.py:2512`).
- **The target runs one forward over K+1 positions.** `gpu_model_runner.py:2803` `_calc_spec_decode_metadata` builds `num_sampled_tokens = num_draft_tokens + 1` logit indices per request, splitting them into `target_logits_indices` and `bonus_logits_indices`.

## 3. Accept/reject (`v1/sample/rejection_sampler.py`)
- **Greedy path.** Kernel at `:726`: `token_id = target_argmax_id; rejected = draft_token_id != target_argmax_id`. Even the rejected position emits the target's argmax. It only runs `if not sampling_metadata.all_random` (`:469`).
- **Random path.** Kernel at `:829`: `accepted = draft_prob > 0 and target_prob / draft_prob >= uniform_prob`. With greedy drafts, `NO_DRAFT_PROBS` sets `draft_prob = 1`, so the token is accepted with probability p_target(draft). On rejection it emits a recovered token sampled from `max(p - q, 0)` (`:1061`). With no draft probs, that means the target distribution with the draft token masked out (`:1045-1048`, Gumbel/`inv_q` argmax).
- **Bonus token.** It is sampled by the normal sampler from the logits after the last draft (`:148-162`) and appended only `if not rejected` (`:775`, `:893`). The output is accepted prefix + one recovered or bonus token (docstring `:64`), so each step emits 1 to K+1 tokens.
- **Accepted prefix and losslessness.** The prefix runs until the first rejection; later positions stay `PLACEHOLDER_TOKEN_ID=-1` (`:38`, `:444`). Losslessness is the standard speculative-sampling result: accept with min(1, p/q), else resample from norm(max(p - q, 0)). Penalties and processors are applied to the target logits first (`:176-183`). `-1` padded drafts are always rejected (`:864`).

## 4. KV cache and state consistency
- **Slots for drafts are allocated up front.** `scheduler.py:747` calls `allocate_slots(request, num_new_tokens, num_lookahead_tokens=self.num_lookahead_tokens)`. In `v1/core/kv_cache_manager.py:539`, `num_tokens_need_slot = num_tokens_main_model + num_lookahead_tokens`. `num_lookahead_tokens` is K for eagle and draft_model and 0 for ngram (`config/vllm.py:629-654`), and covers the drafter writing past the target's query range.
- **Rejected KV is never committed.** Prefix caching only caches `min(total_computed + num_new, request.num_tokens)` (`kv_cache_manager.py:608`). The comment says this excludes "draft tokens that could be rejected".
- **Rollback.** `update_from_output` (`scheduler.py:1967`): `num_accepted = len(generated) - num_sampled`, `num_rejected = num_draft - num_accepted`, then `request.num_computed_tokens -= num_rejected` (`:2059-2069`). The block slots stay allocated and the stale KV is simply overwritten when those positions are scheduled again. Nothing is explicitly zeroed.
- **Draft KV consistency (padded drafter batch, the default).** `prepare_inputs_padded` (`llm_base_proposer.py:1099`) feeds all K+1 target positions to the drafter, using rejected positions "as padding". It samples at `token_indices_to_sample` (last valid position) and sets `seq_lens -= num_rejected_tokens_gpu` (`:684`). The rejected entries are then masked out and overwritten by later draft steps or the next step's prefill pass.

## 5. Continuation
- **Next-step state.** The accepted and bonus tokens are appended to the request, and `num_computed_tokens` points just past the last token whose KV the target wrote. The next schedule therefore runs `[last emitted token] + K new drafts` at those positions (`scheduler.py:677`).
- **Drafter continuation.** The drafter's first pass resumes from `next_token_ids` (the last emitted token) inserted at the sample index (`:847-850`), so its KV is rebuilt from the target-verified tokens every step. It never accumulates divergent state.

## 6. Interaction with continuous batching
- **Budget.** Draft tokens count fully against `token_budget = max_num_scheduled_tokens` (`scheduler.py:582`, `:825`). draft_model also reserves `draft_slots = 1` per request from `max_num_batched_tokens` (`:583-584`, `:826`). If the budget runs short, `num_new_tokens` shrinks and the drafts are truncated (`:839-840`).
- **No load-based disabling.** `disable_by_batch_size` does not exist in 0.31.0 (grep finds nothing). The only adaptation is opt-in Dynamic SD: `num_speculative_tokens_per_batch_size` (`config/speculative.py:492`) is converted to a lookup from batch size to K (`v1/spec_decode/dynamic/utils.py:77`) and applied with `dynamic_sd_lookup[len(num_scheduled_tokens)]` (`scheduler.py:1446-1449`). With K=0, the drafter still runs its prefill pass to stay in sync (`llm_base_proposer.py:614-626`). Drafting is also skipped near `max_model_len` (`gpu_model_runner.py:4514`).
- **Target CUDA graphs.** `uniform_decode_query_len = 1 + self.num_spec_tokens` (`gpu_model_runner.py:883`). Capture sizes are rounded up to multiples of K+1 (`config/compilation.py:1536-1580`), and the maximum capture size is `max_num_seqs*(K+1)*2` capped at 512 (1024 on Blackwell) (`config/vllm.py:2394`). FULL decode graphs need `max_num_scheduled_tokens == K+1` for every request (`gpu_model_runner.py:3853`). New decode requests are padded with `-1` drafts to preserve that (`scheduler.py:1086-1096`, `:1318`).

## 7. Metrics
- **Accumulation.** `SpecDecodingStats.observe_draft` (`v1/spec_decode/metrics.py:41-49`) does `num_drafts += 1`, adds draft and accepted tokens, and increments `per_pos[i]` for `i < num_accepted`. Prometheus counters are incremented at `:269-281`.
- **Call condition.** It is called from `scheduler.py:2054-2075` only when `scheduled_spec_decode_tokens[req]` is non-empty. A draft is therefore one request-step with at least one scheduled draft token.
- **ngram with no match.** The draft is `[]` and is not counted. A partial match (fewer than K tokens) counts as one draft with fewer draft tokens.
- **Grammar-invalidated tokens** are subtracted from draft tokens (`:2916`). Padded `-1` drafts on new decode requests (`:1318`) do count as drafts with 0 accepted. This is a small bias in mean acceptance length (my reading; not verified at runtime).
- **Derived values.** Mean acceptance length is `1 + accepted/drafts` (`metrics.py:114`). Per-position rate is `per_pos/num_drafts` (`:117`), so short ngram drafts lower the later-position rates.

## Implications for benchmarks
- **draft_model roughly halves KV capacity (an estimate).** Qwen3-0.6B KV per token (28 layers × 8 KV heads × 128) is 1.17× the target's (48 × 4 × 128), and both share one pool. That works out to about 46% of the baseline KV capacity, so preemption or queueing should start at lower concurrency. eagle3 (1 layer × 4 heads) adds about 2%.
- **Under load, verify compute grows about (K+1)×.** Every decode request spends K+1 budget tokens whether its drafts are accepted or not. The budget is about K+1 times tighter, nothing turns speculation off automatically, and the throughput gain should shrink, or go negative, at high concurrency unless you configure Dynamic SD.
- **The MoE target makes this worse (an inference).** K+1 query tokens per request route to more distinct experts per step, so verify cost on Qwen3-30B-A3B grows closer to linearly in K than it does for a dense model at small batch. The A3B sparsity makes the baseline decode step cheap, which caps the speedup.
- **draft_model drafting cost grows with K.** It is one pass over all K+1 tokens plus K-1 sequential 0.6B forwards with piecewise (not full) CUDA graphs. Expect the draft overhead to rise linearly with K. eagle3 makes the same number of passes but each is one layer, so it is far cheaper.
- **ngram is free when it misses but fragments graphs.** No match costs nothing (no drafts, no metric). Variable draft lengths break the uniform K+1 decode shape, so FULL CUDA graphs are lost, and CPU ngram also disables async scheduling (`config/vllm.py:1576-1601`).
- **Greedy (temperature 0) acceptance is exact-match.** It is deterministic and gives the upper bound. At temperature > 0 with greedy drafts, acceptance is p_target(draft), which is lower than with probabilistic drafts.
- **Report acceptance from the counters.** Use `num_accepted_tokens/num_draft_tokens` and `1 + accepted/drafts`. For ngram these exclude steps with no match, so they overstate per-step benefit; pair them with end-to-end tokens/s.
